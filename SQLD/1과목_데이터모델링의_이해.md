## 1장. 데이터 모델링의 이해

### 1-1. 모델링과 3가지 관점

**모델링** = 현실세계를 추상화·단순화하여 일정한 표기법으로 명확히 표현하는 것. (DB 구축을 위한 분석·설계 과정)

**모델링의 3대 특징** — "구·단·명"
- **추상화**: 현실을 일정 형식에 맞춰 간략히 표현
- **단순화**: 약속된 규약/제한된 표기로 표현
- **명확화(정확화)**: 애매모호함(불분명함)을 제거하고 정확히 기술

**모델링의 3가지 관점**
- **데이터 관점(What)**: 무엇이 필요한가 — 업무와 데이터의 관계
- **프로세스 관점(How)**: 어떤 절차/순서인가 — 업무가 하는 일
- **상관 관점(Interaction)**: 업무 처리 방법에 따라 데이터가 받는 영향

> ⚠️ **함정**: 모델링 특징에 "**일반화**"나 "**구체화**"가 보기로 나오면 **오답**. (추상화·단순화·명확화가 정답)

---

### 1-2. 데이터 모델링의 3단계 ⭐

| 단계 | 특징 | 핵심 키워드 |
|------|------|-------------|
| **개념적 모델링** | 업무중심·포괄적, **추상화 수준 가장 높음**, 핵심 Entity 추출, ERD 도출, 전사적 수행 | 추상화 최고, ERD |
| **논리적 모델링** | 테이블 도출, **Key·속성·관계 표현**, 정규화 적용 → 데이터 일관성 확보 | 정규화, 재사용성 |
| **물리적 모델링** | DBMS 특성에 맞게 인덱스·저장방식 등 물리적 성격 고려 | 성능, 저장구조 |

> ⚠️ **함정 1**: "추상화 수준이 가장 높은 단계" → **개념적** 모델링. (논리/물리 아님)
> ⚠️ **함정 2**: 정규화는 **논리적** 모델링 단계의 활동. (물리 X)
> ⚠️ **함정 3**: 순서는 **개념 → 논리 → 물리**.

---

### 1-3. 데이터 독립성

- **논리적 독립성**: 외부 스키마 ↔ 개념 스키마 매핑으로 보장. 개념 스키마가 바뀌어도 외부 스키마(응용)에 영향 X
- **물리적 독립성**: 개념 스키마 ↔ 내부 스키마 매핑으로 보장. 내부 스키마(저장장치)가 바뀌어도 외부/개념에 영향 X

> ⚠️ **함정**: "논리적 독립성 = 외부↔개념", "물리적 독립성 = 개념↔내부". 짝을 바꿔서 내는 게 단골 함정.

---

### 1-4. 데이터베이스 3단계 구조 ⭐⭐

| 단계 | 스키마 | 관점 |
|------|--------|------|
| 외부 단계 | **외부 스키마** | 사용자 개개인·View(여러 사용자 관점), DB 이용자 관점 |
| 개념 단계 | **개념 스키마** | 모든 사용자 관점을 **통합**, 조직 전체·설계자 관점 |
| 내부 단계 | **내부 스키마** | DB가 물리적으로 저장된 형식, 개발자·저장장치 관점 |

- 외부/개념 사이 = **논리적 데이터 독립성**
- 개념/내부 사이 = **물리적 데이터 독립성**
- 데이터 모델링 = 통합 관점의 **개념 스키마**를 만들어 가는 과정

---

### 1-5. 데이터 모델링의 3가지 구성 요소

| 구성 요소 | 의미 | 예 |
|-----------|------|-----|
| **Entity** | 업무와 관련된 어떤 것(Things) | 학생, 과목 |
| **Attribute** | 어떤 것이 갖는 성격 | 이름, 학점 |
| **Relationship** | 어떤 것 간의 관계 | 수강하다 |

- **인스턴스(Instance)**: 특정 시점에 DB에 실제로 저장된 데이터 값

> **용어 대응표 (자주 헷갈림)**
> | 개념 | 복수/집합(타입·클래스) | 개별/단수(어커런스·인스턴스) |
> |------|------|------|
> | 어떤 것 | 엔터티 타입 / 엔터티 | 엔터티 / 인스턴스·어커런스 |
> | 연관 | 관계 | 페어링 |
> | 성격 | 속성 | 속성값 |

## 2장. 엔터티 (Entity)

### 2-1. 엔터티 개념
- 업무에 필요하고 유용한 정보를 저장·관리하기 위한 **집합**
- **엔터티 = 인스턴스의 집합**

### 2-2. 엔터티 유형 ⭐

**① 유·무형에 따른 분류**

| 유형 | 특징 | 예 |
|------|------|-----|
| 유형(Tangible) | 물리적 형태 O, 안정적·지속적 | 교수, 강의실, 물품, 사원 |
| 개념(Conceptual) | 물리적 형태 X, 관리할 개념적 정보 | 수업, 보험상품, 시스템, 조직 |
| 사건(Event) | 업무 수행 중 발생, 발생량 많음(통계 활용) | 수강신청, 주문, 입금, 미납 |

**② 발생시점에 따른 분류**

| 유형 | 특징 | 예 |
|------|------|-----|
| 기본(Key) | 본래 존재, 독립적 생성, 타 엔터티의 **부모** 역할, 자신의 고유 주식별자 | 사원, 부서, 고객, 상품, 자재 |
| 중심(Main) | 기본 엔터티로부터 발생, 업무의 중심 | 접수, 계약, 주문 |
| 행위(Action) | 2개 이상 부모로부터 발생, 자주 변경·증가 | 주문내역, 계약진행 |

> ⚠️ **함정**: "수강신청, 주문"은 **사건(Event)** 엔터티. "혼자 존재 못하고 다른 엔터티에 의존" → 행위/사건 엔터티 특징.

### 2-3. 엔터티 명명 규칙 / 발생 규칙
- 현업 업무에서 사용하는 용어 사용, 약어 지양, 유일한 이름
- **1개 엔터티는 2개 이상의 인스턴스**를 가져야 함
- **1개 엔터티는 2개 이상의 속성**을 가져야 함
- 1개 속성은 1개 속성값을 가짐

---

## 3장. 속성 (Attribute)

### 3-1. 속성 정의
- **업무에서 관리하고자 하는, 의미상 더 이상 분리되지 않는 최소의 데이터 단위**
- 예: 나이, 이름 (O) / 신상정보(→ 이름·주소로 분리 가능하므로 속성 X)

### 3-2. 엔터티·인스턴스·속성·속성값의 관계 ⭐
- 1개 엔터티 = 2개 이상 인스턴스
- 1개 엔터티 = 2개 이상 속성
- **1개 속성 = 1개 속성값** (다중값이면 별도 엔터티로 분리 → 1차 정규화)

### 3-3. 속성의 분류

**① 특성(성질)에 따른 분류** ⭐
| 종류 | 설명 | 예 |
|------|------|-----|
| 기본(Basic) | 업무로부터 추출한 일반적 속성 | 회원ID, 이름, 주문일자 |
| 설계(Designed) | 업무 규칙화 위해 새로 만든 속성(코드성, 일련번호) | 상품코드, 지점코드 |
| 파생(Derived) | 다른 속성에서 유도·계산된 값(통계) | 합계, 총액 |

> ⚠️ **파생 속성**: 조회 성능을 위해 미리 계산해 저장. **가급적 적게** 정의. 관련 값 업데이트 시 재계산 부담.

**② 구성방식(분해 여부)에 따른** — PK 속성 / FK 속성 / 일반 속성
**③ 속성값 수에 따른** — 단일값 / 다중값(→1차 정규화 or 별도 엔터티)
**④ 분리 가능성에 따른** — 단순(Simple) / 복합(Composite, 예: 주소)

### 3-4. 도메인(Domain)
- 각 속성이 가질 수 있는 **값의 범위**(데이터 타입·크기·제약)
- 예: 학점 → 0.0 ~ 4.5 실수

---

## 4장. 관계 (Relationship)

### 4-1. 관계 정의 / 페어링
- **관계**: 엔터티 인스턴스 사이의 논리적 연관성
- **페어링(Pairing)**: 인스턴스가 개별적으로 관계를 맺는 것. 관계는 페어링의 집합.

### 4-2. 관계의 분류
| 분류 | UML 표현 | 표기 | 소스코드 |
|------|----------|------|----------|
| **존재에 의한 관계** | 연관관계 | 실선 | 멤버변수로 선언 |
| **행위에 의한 관계** | 의존관계 | 점선 | 오퍼레이션(메서드) 파라미터로 이용 |

> ⚠️ ERD에서는 UML과 달리 존재/행위 관계를 **구분하지 않고** 표현.

### 4-3. 관계의 표기법(3요소)
- **관계명**: 관계 이름 (애매한 동사 지양, 현재형)
- **관계 차수(Degree/Cardinality)**: 참여 인스턴스 수 — 1:1, 1:N, M:N
- **관계선택사양(선택성)**: 필수참여(표기 |) / 선택참여(표기 ○)

### 4-4. 관계 체크사항
- 두 엔터티 사이 연관 규칙 존재? 정보의 조합 발생? 업무기술서에 규칙 서술? **동사**가 있는가?

## 5장. 식별자 (Identifier) ⭐⭐

### 5-1. 식별자 개념
- 엔터티를 **대표**할 수 있는 속성, 각 인스턴스를 **구분**해주는 속성
- 하나의 엔터티는 반드시 **하나의 유일한 식별자**가 존재
- 용어: **식별자** = 논리 모델링 단계 / **키(Key)** = 물리 모델링 단계

### 5-2. 식별자 특징 (4가지)
| 특징 | 설명 |
|------|------|
| **유일성** | 주식별자로 모든 인스턴스를 유일하게 구분 |
| **최소성** | 유일성 만족하는 **최소 개수**의 속성 (하나로 충분하면 추가 X) |
| **불변성** | 한번 지정되면 값이 변하면 안 됨 |
| **존재성** | 값이 반드시 존재해야 함 (**Null 허용 X**) |

### 5-3. 식별자의 분류 ⭐
| 분류 기준 | 식별자 | 설명 |
|-----------|--------|------|
| **대표성 여부** | 주식별자(Primary) | 대표 O, 참조관계 연결 가능 |
| | 보조식별자(Candidate) | 구분은 가능하나 대표성 X, 참조관계 연결 불가 |
| **스스로 생성 여부** | 내부식별자 | 엔터티 내부에서 스스로 생성 |
| | 외부식별자(Foreign) | 관계를 통해 유입되는 타 엔터티 식별자 |
| **속성 수** | 단일식별자 | 하나의 속성 |
| | 복합식별자 | 둘 이상 속성 |
| **대체 여부** | 본질식별자 | 업무에 의해 만들어지는 식별자 |
| | 인조식별자 | 원조 복잡해 인위적으로 만든 식별자 |

> **암기 포인트**: 보통 하나의 속성은 → **주식별자·내부식별자·단일식별자·본질식별자**인 경우가 많다.
> **본질 = 원조, 인조 = 대리.**

### 5-4. 키(Key)의 종류 ⭐
| 키 | 유일성 | 최소성 | 설명 |
|-----|--------|--------|------|
| **슈퍼키(Super)** | O | **X** | 유일성만 만족 |
| **후보키(Candidate)** | O | O | 유일성+최소성 |
| **기본키(Primary)** | O | O | 후보키 중 대표로 선정 |
| **대체키(Alternate)** | O | O | 후보키 중 기본키 제외한 나머지 |

> ⚠️ **함정**: 슈퍼키는 **최소성 X**. "유일성만 만족" → 슈퍼키.

### 5-5. 식별자 관계 vs 비식별자 관계 ⭐⭐
| 항목 | 식별자 관계 | 비식별자 관계 |
|------|-------------|---------------|
| 목적 | 강한 연결관계 | 약한 연결관계 |
| 부모키 상속 위치 | 자식의 **주식별자(PK)**로 상속 | 자식의 **일반 속성(FK)**으로 상속 |
| 표기법 | **실선** | **점선** |
| 부모 존재 | 부모 있어야 자식 생성 가능(Strong→Weak) | 부모 없이 자식 생성 가능 |

**비식별자 관계를 쓰는 경우**: 자식의 독립적 PK 필요, 부모-자식 관계가 약함, 부모 인스턴스가 자식보다 먼저 소멸, SQL 조인 최소화·PK 단순화 필요할 때.

> ⚠️ **함정**: "실선 = 식별자관계 = 부모 PK가 자식 PK로", "점선 = 비식별자관계 = 부모 PK가 자식 일반속성(FK)로". 짝 바꿔 출제 단골.

## 6장. 데이터 모델과 성능 — 정규화 ⭐⭐⭐

### 6-1. 정규화 정의
- **최소한의 데이터 중복, 최대한의 데이터 유연성, 데이터 일관성**을 위해 데이터를 분리하는 과정
- 논리 데이터 모델(개념·물리 X) 상세화의 대표 활동
- 목적: 함수적 종속을 가진 일반 속성을 의존자로 하여 **입력/수정/삭제 이상(Anomaly)** 제거

### 6-2. 이상 현상(Anomaly) 3가지
| 이상 | 설명 |
|------|------|
| **삭제 이상** | 삭제 시 원치 않는 다른 정보까지 삭제 |
| **삽입 이상** | 원치 않는 값 때문에 삽입 불가(불필요 값 강제) |
| **갱신 이상** | 중복 데이터 중 일부만 갱신되어 불일치 |

### 6-3. 정규형(NF) 절차 ⭐⭐
| 단계 | 제거 대상 | 핵심 |
|------|-----------|------|
| **1NF** | (원자성) | 모든 속성은 하나의 값(원자값), 중복 인스턴스 X |
| **2NF** | **부분함수종속** 제거 | 일반속성이 주식별자 **전체**에 종속 |
| **3NF** | **이행함수종속** 제거 | 일반속성 간 종속 X (A→B, B→C 제거) |
| **BCNF** | 결정자 중 후보키 아닌 것 제거 | 모든 **결정자가 후보키** |
| **4NF** | **다치종속** 제거 | 다중값 종속 없음 |
| **5NF** | **조인종속** 제거 | 분해 후 조인 시 손실 없음(매우 희귀) |

> ⚠️ 이전 단계 정규형을 만족해야 다음 단계 진행 가능. (포함관계: 1NF ⊃ 2NF ⊃ 3NF ⊃ BCNF ⊃ 4NF ⊃ 5NF)

### 6-4. 함수적 종속(FD)
- x값 하나에 y값이 유일하게 대응 → "x가 y를 결정한다(x→y)"
- **부분함수종속**: 복합 PK의 **일부**가 일반속성을 결정 → 2NF 위반
- **이행함수종속**: PK가 아닌 속성이 다른 속성을 결정(A→B→C) → 3NF 위반

> 💡 핵심 한 줄: **"정규화는 결정자별로 테이블을 쪼개되, 결정자는 원 테이블에도 남긴다."**

### 6-5. 정규화와 성능
- 정규화 → 중복 감소 → 용량 최소화 → **입력/수정/삭제 성능 향상**
- 단, **조회(SELECT)는 JOIN이 늘어 성능 저하될 수 있음** ⚠️

### 6-6. 반정규화(Denormalization)
- DB 성능 향상 위해 **중복 허용·조인 감소**시키는 기법 (≠ 비정규화)
- **조회 속도 ↑, 유연성·입력/수정/삭제 성능 ↓**
- 수행 경우: 조인 과다로 성능 저하 예상, 대량 범위 자주 처리, 요약/집계 자주 요구
- ⚠️ 반정규화가 조회 성능 향상을 **항상 보장하는 것은 아니다.**

## 7장. 관계와 조인 / 트랜잭션 / NULL

### 7-1. 조인(JOIN)
- 식별자를 상속하고, 상속된 속성을 **매핑키(JOIN KEY)**로 활용해 데이터를 결합
- JOIN KEY는 보통 **외래키(FK)**로 설정
- **셀프 조인**: 하나의 엔터티 내에서 인스턴스끼리 계층 구조를 가질 때(같은 테이블 여러 번 조인) — 예: 직원-상사

### 7-2. 상호 배타적 관계(Exclusive-OR)
- 하나의 부모가 2개 자식 중 **하나만** 관계 유지 (예: 주문은 개인고객 or 법인고객 중 하나)

### 7-3. 모델이 표현하는 트랜잭션 ⭐
- **트랜잭션**: 업무 처리를 위한 **논리적 작업 단위**(하나의 연속 업무)
- 트랜잭션에 의한 관계 → **필수적 관계** 형태
- 속한 동작은 **모두 성공 or 모두 취소(All or Nothing)** — 원자성
- 예) 계좌이체: A -100 / B +100 은 동시에 성공/취소되어야 함. 부분 COMMIT 불가.

**트랜잭션 특징 (ACID)**
| 특성 | 설명 |
|------|------|
| 원자성(Atomicity) | 전부 처리 or 전부 취소 |
| 일관성(Consistency) | 실행 전후 DB가 일관된 상태 유지 |
| 격리성(Isolation) | 실행 중 중간결과를 다른 트랜잭션이 접근 불가 |
| 지속성(Durability) | 성공 결과는 영구 반영 |

### 7-4. NULL 속성의 이해 ⭐⭐⭐
- NULL = **아직 정의되지 않은 값**(모르는 값, 값의 부재). 0(숫자)이나 공백(문자)과 **다름**
- NULL을 포함하는 **연산 결과는 NULL** (모르는 값 + 숫자 = 모르는 값)
- **NULL과의 모든 비교(IS NULL 제외)는 unknown(알 수 없음) 반환** → NULL = NULL 은 참이 아님
- **집계함수 계산 시 NULL은 0이 아니라 계산에서 제외**

**집계함수에서 NULL 취급 (⭐ 시험 단골)**
- NULL 값은 집계함수에서 **무시**됨
- **COUNT(*)** = NULL 포함 전체 행 개수
- **COUNT(컬럼)** = 해당 컬럼의 NULL 제외 개수
- PK 컬럼은 NULL 불가 → 항상 `COUNT(*) = COUNT(PK)`
- 전체 행 평균 = `SUM(col) / COUNT(*)` (AVG(col)는 NULL 제외라 값이 다를 수 있음 ⚠️)
- **NVL(C, 0)** / ISNULL: NULL을 다른 값으로 치환

### 7-5. 본질식별자 vs 인조식별자 ⭐
- **본질(원조) 식별자**: 업무에 의해 만들어지는 꼭 필요한 식별자 (예: 학번, 주민번호, 사번)
- **인조(대리) 식별자**: 원조가 너무 복잡할 때 인위적으로 만든 식별자 (자동증가 일련번호, 시퀀스)

**인조식별자 장점**: 시퀀스/제약조건으로 쉽게 생성 → 개발 편의성 ↑ (시간↓, 비용↓)
**인조식별자 단점**: ⚠️
- 중복 데이터 발생 가능성 → 데이터 품질 저하 (원래 PK로는 막던 중복을 못 막음)
- 불필요한 인덱스 생성 → 저장공간 낭비, DML 성능 저하
- 결국 검색은 원래 업무 키(예: 주문번호+상품번호)로 WHERE절 작성하게 됨
- 필요한 경우에만 사용하는 것이 바람직
